1. TOPOLOGIA
-------------------------------------------------------------------------------------

Router: 5 x Router-PT (router generico di Packet Tracer). Le LAN usano le porte
FastEthernet in rame gia' presenti (Fa0/0, e Fa1/0 su R-SEDE); i collegamenti tra
router sono in Gigabit Ethernet, su moduli PT-ROUTER-NM-1CGE aggiunti negli slot
liberi 6, 7 (e 8 su R-DC per la WAN). Ogni modulo diventa GigabitEthernet<slot>/0.

Anello: R-SEDE -- R-SERRA -- R-DC -- R-MAG -- R-SEDE (4 dorsali Gigabit /30)

Convenzione sulle dorsali: su ogni router dell'anello la Gi6/0 va verso il router
successivo in senso orario (SEDE->SERRA->DC->MAG->SEDE) e prende il primo IP del
/30; la Gi7/0 arriva dal router precedente e prende il secondo IP.
Le dorsali sono collegamenti diretti router-router con cavo Copper Cross-Over.

Reti locali:
  - Sede/Uffici  : su R-SEDE Fa0/0 (switch SW-UFFICI, PC cablati)
  - WLAN Sede    : su R-SEDE Fa1/0 (switch SW-WLAN, WLC-SEDE + 2 LAP + client Wi-Fi)
  - Serra/IoT    : su R-SERRA Fa0/0 (switch SW-SERRA, AP-SERRA, sensori e attuatori Wi-Fi)
  - Magazzino    : su R-MAG Fa0/0 (switch SW-MAG, PC magazzino)
  - Data Center  : su R-DC Fa0/0 (switch SW-DC, SRV-DHCP-DNS, SRV-IOT)
  - Internet     : rete del provider dietro R-ISP (server WEB-ISP)

sceglie il prefisso piu' piccolo che soddisfa  host richiesti + 2 <= 2^h.

4. ROUTING STATICO
-------------------------------------------------------------------------------------

4.1 Criteri per ridurre il numero di rotte
  a) Default route sui router dell'anello verso l'uscita Internet (R-DC): copre in una
     sola riga Data Center, WAN e Internet. R-DC ha la default verso R-ISP.
  b) Summary 10.20.0.0/24: Uffici, WLAN, IoT e Magazzino stanno tutte in 10.20.0.0/24,
     quindi una sola rotta le copre. Le eccezioni sono gestite dal longest prefix match
     (una rete direttamente connessa o una rotta /27 vincono sul /24).
  c) Su R-ISP una sola rotta riassuntiva 10.20.0.0/22 per tutta l'azienda.
  d) Backup "implicito": quando sparisce una rotta specifica (link giu'), il traffico
     ricade sulla rotta piu' larga rimasta (default o summary). Su R-MAG questa punta
     gia' dal lato giusto dell'anello (se cade L4 la rotta 10.20.0.0/24 sparisce e
     il traffico per la Sede ricade sulla default via R-DC), quindi li' non serve
     una floating. Negli altri casi (R-SEDE rete IoT, R-SERRA reti Sede, R-DC
     Magazzino) la rotta larga punta verso un router che rimanda indietro il
     pacchetto: sono proprio i guasti L1 e L3 descritti nel capitolo 5.3.
  e) Rotte di backup (floating static) con distanza amministrativa 10: restano
     nascoste finche' la rotta primaria (AD 1) e' presente e compaiono in
     "show ip route" solo quando l'interfaccia del percorso primario va giu'.

Totale: 17 rotte statiche (13 primarie + 4 floating).

4.3 Percorsi in condizioni normali
Tutti i percorsi sono minimi (al massimo 2 router di transito nell'anello):
  Uffici/WLAN -> DC/Internet : SEDE -> MAG -> DC
  DC/Internet -> Uffici/WLAN : DC -> SERRA -> SEDE
  IoT Serra  <-> DC          : SERRA <-> DC
  Magazzino  <-> DC          : MAG <-> DC
  Uffici     <-> IoT Serra   : SEDE <-> SERRA
  Uffici     <-> Magazzino   : SEDE <-> MAG
  IoT Serra   -> Magazzino   : SERRA -> DC -> MAG  (ritorno MAG -> SEDE -> SERRA)

Il traffico tra Sede e Data Center e' asimmetrico (andata via R-MAG, ritorno via
R-SERRA). E' una scelta voluta: e' la combinazione che protegge piu' guasti (cap. 5.3).

5.3 Prova di guasto di un link dell'anello

Come funzionano le floating static: quando un'interfaccia va in down, la rete
connessa sparisce, il next hop non e' piu' raggiungibile e la rotta primaria viene
tolta dalla tabella. Al suo posto compare la rotta di backup con AD 10.
Limite: un router si accorge solo dei guasti sui SUOI link. Gli altri router
continuano a usare le rotte primarie, perche' con il routing statico non c'e'
scambio di informazioni tra router.

PROVA 1 - spengo L2 (R-SERRA Gi6/0 "shutdown"):
  Prima  R-SERRA:  S*  0.0.0.0/0 [1/0] via 10.20.1.22
         R-DC   :  S   10.20.0.0/24 [1/0] via 10.20.1.21
  Dopo   R-SERRA:  S*  0.0.0.0/0 [10/0] via 10.20.1.17       <- backup via R-SEDE
         R-DC   :  S   10.20.0.0/24 [10/0] via 10.20.1.26    <- backup via R-MAG
  Ping: tutti continuano a raggiungere tutti (al massimo si perde il primo pacchetto).
  Esempio IoT -> SRV-IOT: SERRA -> SEDE -> MAG -> DC; risposta DC -> MAG -> SEDE -> SERRA.
  La serra resta collegata all'IoT Server.

PROVA 2 - spengo L4 (R-MAG Gi6/0 "shutdown"):
  Dopo   R-SEDE :  S*  0.0.0.0/0 [10/0] via 10.20.1.18       <- backup via R-SERRA
         R-MAG  :  la rotta 10.20.0.0/24 sparisce, il traffico per la Sede
                   ricade sulla default via R-DC (backup implicito)
  Ping: tutti continuano a raggiungere tutti.

PROVA 3 - spengo L1 o L3: alcuni ping falliscono con "Request timed out" o
"TTL expired in transit".
  Con L1 giu' in "show ip route" non compare nessuna floating: le default
  primarie di R-SEDE e R-SERRA restano valide; spariscono solo le rotte verso il
  vicino (rete IoT su R-SEDE, Uffici e WLAN su R-SERRA) e il traffico ricade
  sulle default, che puntano dalla parte sbagliata.
  Con L3 giu' su R-MAG compare S* 0.0.0.0/0 [10/0] via 10.20.1.30, ma e' proprio
  questa rotta a rimandare indietro il traffico diretto al Data Center.
  Esempio L1 giu', ping da R-DC verso gli Uffici:
     R-DC non sa del guasto e manda il pacchetto a R-SERRA (summary primario);
     R-SERRA ha perso la rotta verso la Sede, usa la default primaria e lo
     rimanda a R-DC -> il pacchetto rimbalza R-DC <-> R-SERRA finche' il TTL
     arriva a 0 (routing loop). In Simulation mode si vede il pacchetto che fa
     avanti e indietro.
  Esempio L3 giu', ping da Uffici verso il DC: R-SEDE manda a R-MAG, R-MAG usa
     la default di backup e lo rimanda a R-SEDE -> loop SEDE <-> MAG.

Risultati dei ping per ogni guasto (OK = andata e ritorno riusciti):
  +---------------+---------------------------------------------------------------+
  | Link giu'     | Risultato                                                     |
  +---------------+---------------------------------------------------------------+
  | nessuno       | tutti OK                                                      |
  | L2 SERRA-DC   | tutti OK                                                      |
  | L4 MAG-SEDE   | tutti OK                                                      |
  | L1 SEDE-SERRA | OK:   IoT<->DC/Internet, Magazzino<->DC/Internet,             |
  |               |       Uffici/WLAN<->Magazzino                                 |
  |               | LOOP: Uffici/WLAN<->DC/Internet, IoT<->Uffici/WLAN/Magazzino  |
  | L3 DC-MAG     | OK:   IoT<->DC/Internet, Uffici/WLAN<->IoT/Magazzino          |
  |               | LOOP: Uffici/WLAN<->DC/Internet, Magazzino<->DC/Internet,     |
  |               |       IoT<->Magazzino                                         |
  +---------------+---------------------------------------------------------------+

Perche' proprio L2 e L4 sono protetti: con 4 router ad anello e rotte statiche,
per ogni rete di destinazione esiste sempre un link il cui guasto crea un loop
(il router "opposto" non puo' sapere quale lato si e' rotto). I percorsi primari
sono stati scelti in modo che questi link "scoperti" siano sempre gli stessi due
(L1 e L3). Cosi' il guasto di L2 o L4 e' coperto al 100%. Inoltre il collegamento
IoT Serra <-> IoT Server funziona con QUALSIASI link guasto, quindi
l'automazione della serra non si ferma mai. Abbiamo controllato tutte le
combinazioni possibili di percorsi primari: nessuna fa meglio di questa.

Nota sul ping lanciato DAL router: il router usa come sorgente l'IP
dell'interfaccia di uscita. Con L2 giu', R-SERRA esce da Gi7/0 (10.20.1.18) e
la risposta verso la dorsale L1 non ha un percorso alternativo, quindi il ping
dal router fallisce anche se il traffico degli host funziona. Per le prove usare
i PC, oppure il ping esteso con sorgente l'interfaccia LAN (10.20.0.193).

Come si supera il limite: con un protocollo di routing dinamico (es. OSPF) i
router si scambiano lo stato dei link e ricalcolano i percorsi da soli dopo
qualsiasi guasto. Con le sole statiche servirebbe il tracking delle rotte
(IP SLA), che va oltre le richieste del compito.

8. IOT - ILLUMINAZIONE (scheda SBC, programma Python sbc_illuminazione.py)
-------------------------------------------------------------------------------------

Collegamenti alla scheda SBC-SERRA (cavo IoT Custom Cable):
+-------+---------------------+-----------------------------------------------------+
| Porta | Componente          | Funzione                                            |
+-------+---------------------+-----------------------------------------------------+
| A0    | Photo Sensor        | luce misurata (analogRead, 0..1023)                 |
| A1    | Potentiometer       | luce desiderata (analogRead, 0..1023)               |
| D0    | Servo               | tenda: customWrite(angolo), 0 = aperta, 90 = chiusa |
| D1    | LED (lampada)       | intensita': analogWrite 0..1023                     |
+-------+---------------------+-----------------------------------------------------+

Algoritmo (ciclo ogni 0,5 s), errore = luce misurata - luce desiderata:
  - errore > +50 (troppa luce): se la lampada e' accesa si spegne; altrimenti la
    tenda si chiude di una percentuale proporzionale all'eccesso:
        chiusura % = errore x 100 / 512   (limitata a 0..100)
  - errore < -50 (poca luce): se la tenda e' chiusa si riapre; se e' aperta la
    lampada si accende con intensita' proporzionale alla carenza:
        intensita' % = |errore| x 100 / 512   (limitata a 0..100)
  - |errore| <= 50 (luce corretta, banda di tolleranza del 5% circa): tenda e
    lampada mantengono lo stato attuale.
La banda di tolleranza evita che gli attuatori oscillino per piccole variazioni.
Il programma stampa in console ogni cambio di stato (luce, obiettivo, azione).

9. IOT - TEMPERATURA (regole dell'IoT Server)
-------------------------------------------------------------------------------------

Dispositivi (smart device registrati su SRV-IOT, connessi in Wi-Fi a SmartSerra-IoT):
  - Temperature Monitor  -> sensore di temperatura (proprieta' Temperature, gradi C)
  - Furnace              -> riscaldamento (proprieta' On: true/false)
  - Window               -> finestra (proprieta' On: true = aperta)
  - Ceiling Fan          -> ventilatore (proprieta' Status: Off / Low / High)

Soglie scelte:
  riscaldamento ON sotto 16 C, OFF sopra 19 C (isteresi 16-19 C);
  raffrescamento livello 1 sopra 27 C, livello 2 sopra 31 C;
  fine raffrescamento sotto 25 C (isteresi 25-27 C: la finestra non apre e
  chiude in continuazione intorno alla soglia).

+----------------------+-------------------------------------+---------------------------------+
| Regola               | Condizione                          | Azione                          |
+----------------------+-------------------------------------+---------------------------------+
| Riscaldamento_ON     | Temperature < 16                    | Furnace On = true               |
|                      | AND Window On = false               |                                 |
| Riscaldamento_OFF    | Temperature > 19                    | Furnace On = false              |
| Finestra_no_riscald. | Window On = true                    | Furnace On = false              |
| Raffrescamento_1     | Temperature > 27                    | Window On = true                |
|                      | AND Temperature <= 31               | Ceiling Fan Status = Low        |
| Raffrescamento_2     | Temperature > 31                    | Window On = true                |
|                      |                                     | Ceiling Fan Status = High       |
| Fine_raffrescamento  | Temperature < 25                    | Window On = false               |
|                      |                                     | Ceiling Fan Status = Off        |
+----------------------+-------------------------------------+---------------------------------+

Note:
  - La condizione "Window On = false" nella prima regola, insieme alla regola
    Finestra_no_riscald., garantisce che con finestra aperta il riscaldamento sia
    sempre spento (anche se la finestra viene aperta a mano).
  - Raffrescamento_1 e Raffrescamento_2 si escludono a vicenda (<= 31 / > 31),
    cosi' le due regole non comandano il ventilatore in modo opposto.
  - Tra 19 e 25 C e tra 25 e 27 C nessuna regola e' attiva: gli attuatori
    mantengono lo stato (isteresi).
